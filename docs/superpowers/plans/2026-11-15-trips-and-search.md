# Trips and Search: Implementation Plan (UX redesign stage 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Redesign the Trips home page and a search's page so each shows the cheapest trips with flights read (price as the booking link, one label, dates, nights, each way's times, duration and changes), with calendar prices in their own section and calendar, a new-search side panel, and a two-item nav with a limits-and-health top bar.

**Architecture:** The board's pairing group gains each way's duration, stops and airlines, read from the flight list `candidateOf` already holds; a verified figure's legs and seller booking travel in one side list on both `/date-pairs` and the cards read, so every surface links the same target. `core` owns the shared rules (which figures are trips, which dates look lower on the calendar, which count as flights read, a day's mark), and both the api's cards and the web's sections call them. The web gets shared trip and calendar rows and one run-progress component, used by the cards, the Search page's sections and the calendar's day panel; the board, stay strip, legend and engine-facing lines give way to the design's sections and folds; the nav becomes Trips and Settings, with an interim Settings page linking the existing Providers, Alerts and Status views until stages 3 and 4.

**Tech Stack:** TypeScript 5.9, pnpm workspace, Vitest, zod, Hono, React 19, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-08-ux-redesign-design.md` §2–§5 and §7 "Stage 2" (approved by Ian 2026-11-08), mockups `docs/superpowers/specs/2026-11-08-ux-redesign-mockups/01-searches.html` and `02-search.html`. Where design and mockup differ, the design governs; this plan's Rulings refine both and Task 11 folds them back in. The main spec it amends: `docs/superpowers/specs/2026-10-14-flight-price-optimiser-design.md` (revision 69 now). Plan review record: `~/.cache/get-me-there/review-spec/2026-11-15-trips-and-search/zjj0VzsFvj/` (86 findings, all ruled into this revision).

## Global Constraints

- No `as` casts except `as const`/`satisfies`; brands only through core's helpers or zod.
- Tests are event-driven: no sleeps, no poll-until loops; clocks injected or faked. A test that drives many pages states a 15_000 timeout.
- Public wording: the repo's wording rules apply to every doc, comment, test name and commit (the orchestrator gives implementers the three wording greps; run them before every push). Commit messages never name the vendor of the flight pages or describe page reading as anything but "reading". Examples use London → New York or synthetic QQ*/AAA codes; airline examples use names ("Virgin Atlantic"), as list pages state them.
- **Every price shown carries its label.** A price on the wire is a `priceCellSchema` (provenance, `stale`, `ageHours`, `truncated`), never a bare number, and every price on screen goes through `PriceLabel` (or, on a calendar day, carries its label kind and age in its accessible name). Staleness is the wire's `stale` mark, never recomputed.
- One label per price from `figureLabelKind`/`labelDetail` (`apps/web/src/lib/figureLabel.ts`); one booking target from `rowBookingTarget` (moved to `apps/web/src/lib/` in Task 2) and `BookLink`. No surface builds its own label or link wording.
- A synthetic or fixture price is never linked out of the app, and raises `SyntheticBanner`. A page's synthetic check covers every price it shows: trips, the lower-on-calendar figure, calendar days, Price over time points.
- Banned words (main spec §11) and main-path words: no "definition", "cell", "date pair", "basis", "discovery", "itinerary search", "verdict", "reused", "superseded", "billed calls", "on-demand", "trips you can book" on Trips, the Search page's main path, the top bar or Settings. All new copy goes in `COPY` (`apps/web/src/copy.ts`); a sentence that shows a price takes its label as a parameter. Each UI task's Step 1 extends the rendered word sweep (`TRIP_WORDS` in `apps/web/test/views/trip/TripView.test.tsx`, and `apps/web/test/copy/renderedSweep.test.tsx`) to the surfaces it adds.
- **Layout checks:** every UI task calls one shared Playwright helper `expectNoSidewaysScroll(page)` (`document.documentElement.scrollWidth <= innerWidth`, created in Task 4) on each page it changes at 375 px and 1280 px in light and dark, and attaches screenshots at those four settings beside the matching mockup (`01-searches.html`/`02-search.html`) to its report, with a line per visible difference. Dark mode uses shared tokens (Task 4 moves them from `apps/web/src/views/Trip/trip.css` to `apps/web/src/styles/theme.css`): the label-kind tints (seller, google, calendar, cached, not-seen), the heat ramp and its ink, the focus ring.
- `core` keeps 100% coverage and its mutation score; a pure-logic file added to `core` goes in `packages/core/stryker.config.json`. New pure web view-model files go in the web's full-coverage list in `apps/web/vitest.config.ts`. Run each touched package's own `pnpm run test` and `pnpm --filter <pkg> run typecheck` before each commit, one package at a time; a task that changes a contract also runs `pnpm --filter @gmt/web run test` (web fixtures parse contracts).
- **Before every push, run every CI step locally:** `pnpm lint`, `pnpm boundaries`, `pnpm casts`, `pnpm temp-dirs`, `pnpm -r typecheck`, `pnpm -r --workspace-concurrency=1 test`, `pnpm exec vitest run --project scripts`, `pnpm secret-scan`.
- When a task changes an existing test's expectation, its commit message lists each such test and the rule change behind it. A deleted test is listed with the element it pinned and the test that now protects any behaviour that survives.
- Tasks run in order, one at a time: 1 → 2 → … → 11 (they share `copy.ts`, `DatesView.tsx`, `SearchesView.tsx`, the e2e selectors and fixtures).
- The PR lands by squash-merge; plain fix commits are fine. Commit trailer: `MrReasonable <4990954+MrReasonable@users.noreply.github.com>`.

## Rulings made while planning

1. **Legs on read trips.** `LegFacts = Pick<ListedFlight, 'durationMinutes' | 'stops' | 'carriers'>` (core). `PairingCandidate.legs: { out: LegFacts; back: LegFacts }`, filled by `candidateOf` from the outbound and return it chose. The pairing group gains columns `outMinutes`, `outStops`, `outCarriers`, `backMinutes`, `backStops`, `backCarriers` (validators: minutes a positive int; stops an int 0..5; carriers `z.array(pageText).min(1).max(6)`, page text held to `flightTextSchema`); the decoded `DatePairPairing` and `pairingCellSchema` both nest `legs: { out, back }`. `operatedBy` is not carried (the Trip page shows it). The board's flight-lists request stays only for Read flights and `readNow`.
2. **Verified trips' legs and booking.** `/date-pairs` and the cards read both carry `verifiedDetails: { departureDate, returnDate, origin, destination, legs: { out: { durationMinutes, stops }, back: { durationMinutes, stops } }, booking: Booking }[]` for each **current** verified figure, from its chosen result row (`outboundMinutes`, `inboundMinutes`, `stopsOut`, `stopsIn`, `booking`). `rowBookingTarget(pair, figure, cabin, booking: Booking | null)` takes it, so a verified trip links the same target on the card, the Search section, the day panel and the Trip page. A not-current verified figure gets no details and `rowBookingTarget` gives `none`. A verified row never reads `figure.pairing` (it may be another airport pair's trip).
3. **The shared rules live in core** (`packages/core/src/datePairs/views.ts`, 100% coverage, in Stryker): `isTrip(fig)` — basis `pairing` or `verified`, and current (a verified `notSeenInLatest` is not a trip; an older read trip is, with its age); `flightsRead(fig)` — `isTrip(fig)` or `pairingRead` ∈ {`no-pairing-read`, `over-limit`, `sellers-not-read`, `offers-incomplete`, `within-older`, `within-other-limits`} (never `not-read`, `outbound-only`, `list-failed`); `cheapestTrips(ranked)` — the trips in rank order; `lowerOnCalendar(ranked)` — current calendar figures (not superseded) whose `pairingRead` is `not-read`, `outbound-only` or `list-failed`, priced below the cheapest trip (all of them when there is no trip), by price; `overLimitCount(ranked)` — figures with `pairingRead` `over-limit`. The api's cards and the web's sections, run line and folds call these and nothing else.
4. **Cheapest trips** are `cheapestTrips(…)`: cards show three, the Search page five, then 10 more per press. A not-current verified figure shows only in the day panel, labelled "Not seen again", never linked out. When trips were left out for the journey limit, the section says "N dates' trips are over 25h each way" (`overLimitCount`).
5. **Lower on the calendar** is `lowerOnCalendar(…)`: the Search page shows three and "155 dates in all"; each row's one line is its read state from `readStateWords(fig)` (Task 5): "Flights not read", "Return flights not read", "Flights couldn't be read: <reason>". Cards say "155 dates look lower on the calendar, from £372" with the lowest figure's label; a card with no trip says "Calendar prices for 2,146 dates, from £372; no flights read yet." (both through `PriceLabel`).
6. **"Flights read for N dates"** counts `flightsRead` over the pairs in view, across every search so far; it is worded as a total ("23 dates with flights read"), never as the latest run's.
7. **Cards.** `searchCardSchema.cheapest` is replaced by `trips: z.array(cardTripSchema).max(3)` with `cardTripSchema = { figure: datePairFigureSchema, departureDate, returnDate, nights }` (refine: `isTrip(figure)`; the figure holds its airports and `fromEarlierSearch`), `verifiedDetails` (Ruling 2, for the card's trips), `readDates: int`, and `lowerOnCalendar: { count: positive int, cheapest: { price: priceCellSchema, departureDate, returnDate, origin, destination, kind: 'calendar' | 'cached' } } | null`. `latestRun` gains `marks: Record<ReducedMark, number>` over the run's whole snapshot space by core's `reducedMark` per date pair (summing to `datePairs`), plus `browserUnavailable: number` (skips with the browser-unavailable reason); the cells statement returns every date pair's per-run counts and its row bound is pinned (at most one row per date pair of each space) beside the statement count.
8. **"Nothing found" reason and fix.** A card or page whose latest run finished with no trip and no lower-on-calendar figure gives the first matching reason: the run was cancelled or failed (its stop sentence); dates not searched or not reached ("The search stopped before N dates."); the browser was unavailable for N dates; N dates couldn't be read ("the next search tries them again"); the browser is off for this search and the other sources found nothing; every date showed no price ("That isn't the same as no flights."); prices were found but none fit the filters. Each is tested. The fix "Turn on the browser for this search and search again" shows only when the browser is configured (`/providers`) and off for this search: it PUTs the search with `camoufox` added to discovery (other sources kept) and, only if the PUT succeeds, starts it. Otherwise one sentence links to Settings.
9. **Nav: Trips and Settings.** `ViewId` gains `settings`: an interim page (h1 "Settings") with three linked sections, Price sources (→ `view=providers`), Alerts (→ `view=alerts`), System (→ `view=status`), each with one line saying what is there; those views' headings read "Price sources", "Alerts", "System". Stage 3 replaces the page. The old views keep rendering at their URLs. `navItemOf` maps `searches|dates|trip|definitions|history` → Trips and `settings|providers|alerts|status` → Settings. The logo links to Trips. The phone nav is the same two links in one row; the "All views" menu goes.
10. **Top bar.** Left: the health line (`role="status"`), from core's `barSummary`, which returns `{ kind: 'clean' | 'warn' | 'fail' | 'stale' | …; count; name: string | null }` (`name` = the one problem's `label ?? area`, worded through COPY by the web and the CLI): "All working" with a green dot; one problem "<name> needs attention · fix" (warn, amber) or "<name> failing · fix" (fail, red); several "N things need you · fix" (red if any fail); `off` checks never count; the stale, not-answering, sign-in-refused and report-failed words stay.
