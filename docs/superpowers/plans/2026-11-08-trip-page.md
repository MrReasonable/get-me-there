# The Trip Page, One Label per Price, and the Price as Link: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the date-pair detail page with a Trip page that shows the same price as the search page's row, one label per price, and a price that links to the best booking target, with the browser recording the booking page's address.

**Architecture:** The browser worker adds the booking view's address to its booking read (one nullable field validated in `core`), the DB stores it, and an on-demand read stops refusing fresh and unpriced pairs. A new API read, `GET /api/definitions/:id/trip`, assembles one pair of dates from the same functions the search page uses (`datePairFigures` with `pairingsFor`, `assembleFlightLists`), plus the cells' states and a per-run log. `core` owns the two pure rules every surface shares: the label kind of a price and the booking target of a trip. The web gets a `trip` view built from that one response; the old Results view goes.

**Tech Stack:** TypeScript 5.9, pnpm workspace, Vitest, zod, SQLite/Drizzle (drizzle-kit migrations), Hono, React 19, Playwright (worker).

**Spec:** `docs/superpowers/specs/2026-11-08-ux-redesign-design.md` §4–§6 (approved by Ian 2026-11-08), mockup `docs/superpowers/specs/2026-11-08-ux-redesign-mockups/03-trip.html`. Where they differ, the design governs. The main spec it amends: `docs/superpowers/specs/2026-10-14-flight-price-optimiser-design.md` (revision 68 now).

## Global Constraints

- No `as` casts except `as const`/`satisfies`; brands only through core's helpers or zod.
- Tests are event-driven: no sleeps, no poll-until loops; clocks injected or faked. A test that drives many pages states a 15_000 timeout.
- Public wording: the repo's wording rules apply to every doc, comment, test name and commit (the orchestrator gives implementers the three wording greps; run them before every push). Commit messages never name the vendor of the flight pages or describe page reading as anything but "reading". Examples use London → New York or synthetic QQ*/AAA codes.
- The web's banned words (main spec §11: "exhaustive", "all combinations", "every combination", "live", "bookable", "guaranteed", "real-time") and main-path words (no "definition", "cell", "date pair", "basis", "discovery", "itinerary search", "verdict", "reused", "superseded", "billed calls" on the Trip page) are enforced by the existing sweeps; all new copy goes in `COPY` (`apps/web/src/copy.ts`), never inline.
- Label text is exactly: `Seller`, `Google price`, `Google list`, `Calendar`, `Cached`, `Not seen again`, each followed by ` · ` and the age (design §5.1). Booking buttons: `Book on <host> ↗`, `Book on Google Flights ↗`, `Find on Google Flights ↗` (design §5.3).
- Every UI change is checked at 375 px and at desktop width, light and dark, with no sideways scroll, by screenshot (Playwright, the repo's existing tooling).
- `core` keeps 100% coverage and its mutation score; a pure-logic file added to `core` is added to `packages/core/stryker.config.json`. Run each touched package's own `pnpm run test` (it includes coverage) before pushing, one package at a time; also `npx vitest run scripts` and `node scripts/check-mutation-globs.mjs` from the repo root.
- A test file removed is also removed from `apps/web/package.json`'s `test:tz` list, `stryker.config.json` globs and `scripts/workflows.test.mjs` where named.
- When a task changes an existing test's expectation, its commit message lists each such test and the rule change behind it.

## Rulings made while planning

- **On-demand reads never refuse `fresh`**, wherever they're started (the search page's read button too): the operator asking is the reason to read (design §6.1). The `fresh` refusal code goes from engine, route and web.
- **On-demand reads of a pair with no figure** (`no_price` today) read the first airport pair of the search's space (`space.origins[0]` → `space.destinations[0]`) instead of refusing. `no_price` goes.
- **Dates outside the search's window** (departed, or the search's dates changed; old alert links) get their own card state: "These dates are outside this search's dates now." with a link back to the search. Added to the design's table as a ruling.
- **`sellers-not-read` / `offers-incomplete`** (a calendar figure with a read trip beneath it that doesn't lead): the card leads with the calendar price and shows the read trip beneath as "Flights read 3h ago: £Y for the cheapest trip", labelled by its pairing kind, with its legs and its booking target.
- **The Results API stays** (`GET /results`, the cell route): History and the alert emails' builders use them; stage 4 removes what's left. Only the web Results view goes.

## Review Focus

1. **A pair whose newest list failed but an older list read a trip:** the card shows the couldn't-read line above whatever figure the board shows, never a different price. Test in Task 6.
2. **A booking address that isn't the booking page** (another path, another host, a query-only change, over the URL cap): `bookingUrl` is null and the price says "Find on Google Flights ↗". Tests in Tasks 1 and 2.
3. **The Trip page opened with the search page's filters on** (`d.journey`, `d.from`, `d.to`): the card equals the filtered row. Test in Task 5.
4. **An old alert link** (`view=results&basis=verified&row=…`) for dates that departed: lands on the Trip page's outside-window state, not an error. Tests in Tasks 5 and 7.
5. **A long seller name or airline list at 375 px** ("Trip.com Travel Singapore Pte Ltd", three carriers): wraps, no sideways scroll. Screenshot check in Task 8.
