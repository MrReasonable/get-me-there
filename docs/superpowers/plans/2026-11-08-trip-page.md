# The Trip Page, One Label per Price, and the Price as Link: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the date-pair detail page with a Trip page that shows the same price as the search page's row, one label per price, and a price that links to the best booking target, with the browser recording the booking page's address.

**Architecture:** The browser worker adds the booking view's address to its booking read; the API attaches it to a pairing only when that booking read is the pairing's own, and the board's pairing group carries it. On-demand reads stop refusing fresh and unpriced pairs and can name the airport pair. A new read, `GET /api/definitions/:id/trip`, assembles one pair of dates from the board's own composition (one extracted helper), the figure's own cell's flight list, the cells' coverage classes and a per-run log, every price with its provenance. `core` owns the two pure rules every surface shares: a price's label kind and a trip's booking target. The web gets a `trip` view built from that one response; the old Results view goes.

**Tech Stack:** TypeScript 5.9, pnpm workspace, Vitest, zod, SQLite/Drizzle (drizzle-kit 0.31), Hono, React 19, Playwright (worker and web e2e).

**Spec:** `docs/superpowers/specs/2026-11-08-ux-redesign-design.md` §4–§6 (approved by Ian 2026-11-08), mockup `docs/superpowers/specs/2026-11-08-ux-redesign-mockups/03-trip.html`. Where they differ, the design governs; where this plan's Rulings refine the design, Task 9 folds them back in. The main spec it amends: `docs/superpowers/specs/2026-10-14-flight-price-optimiser-design.md` (revision 68 now). ## Global Constraints

- No `as` casts except `as const`/`satisfies`; brands only through core's helpers or zod.
- Tests are event-driven: no sleeps, no poll-until loops; clocks injected or faked. A test that drives many pages states a 15_000 timeout.
- Public wording: the repo's wording rules apply to every doc, comment, test name and commit (the orchestrator gives implementers the three wording greps; run them before every push). Commit messages never name the vendor of the flight pages or describe page reading as anything but "reading". Examples use London → New York or synthetic QQ*/AAA codes.
- Every price on the wire carries its provenance: prices in new contract fields use `priceCellSchema` (`apps`' and `core`'s existing shape: `pricePence`, `provenance`, `stale`, `ageHours`, `truncated`). Staleness shown in the UI is the wire's `stale` mark, never recomputed.
- The web's banned words (main spec §11) and main-path words (no "definition", "cell", "date pair", "basis", "discovery", "itinerary search", "verdict", "reused", "superseded", "billed calls" on the Trip page) are enforced by the existing sweeps; all new copy goes in `COPY` (`apps/web/src/copy.ts`), never inline; a sentence that shows a price takes its label as a parameter, never a literal kind word.
- Label text is exactly `Seller`, `Google price`, `Google list`, `Calendar`, `Cached`, `Not seen again`, then ` · ` and the age formatted as the board formats ages. Booking link texts: `Book on <host> ↗`, `Book on Google Flights ↗`, `Find on Google Flights ↗` (design §5.3). Only an external link carries `↗`, opens in a new tab, and has an accessible name that says so.
- A synthetic or fixture price is never linked out of the app, and any synthetic provenance in a response raises the existing `SyntheticBanner` (as the Results and Dates views do today).
- Every UI change is checked at 375 px and at 1280 px, light and dark: by the Playwright overflow spec (Task 7) and by screenshots attached to the task report.
- `core` keeps 100% coverage and its mutation score; a pure-logic file added to `core` is added to `packages/core/stryker.config.json` and its mutation run passes. Run each touched package's own `pnpm run test` (it includes coverage) and `pnpm --filter <pkg> run typecheck` before each commit, one package at a time; before pushing also `npx vitest run scripts` and `node scripts/check-mutation-globs.mjs` from the repo root.
- One synthetic booking address for every test: `SYNTHETIC_BOOKING_URL` in `packages/core/src/testing/` (Task 1), commented as made up in the real shape (design §6.3), never under a recorded-fixture tree.
- When a task changes an existing test's expectation, its commit message lists each such test and the rule change behind it.
- The PR lands by squash-merge; plain fix commits are fine. Commit trailer: `MrReasonable <4990954+MrReasonable@users.noreply.github.com>`.
- **Deploy:** the worker and the app restart together on merge (the worker answer's `bookingReadSchema` changes on both sides).

## Rulings made while planning

1. **On-demand reads never refuse `fresh`** (Trip page and search page alike): the operator asking is the reason to read (design §6.1). The `fresh` and `no_price` refusal codes go from engine, route, API text and web; `assembleFlightLists`' per-pair `readNow` stops depending on freshness or a figure; `flightListFresh`/`freshPhaseOf` and `Engine.flightListFresh` are deleted if nothing else reads them.
2. **A read names its airport pair.** `readFlightListRequestSchema` gains optional `origin` and `destination` (both or neither; validated inside the search's space, else `outside_space`). The Trip page sends its figure's cell; with no figure and no pair named, the read takes `space.origins[0]` → `space.destinations[0]`.
3. **Dates with no figure that were read by hand** (prov-007, option b): the trip read sends the newest flight list of these dates' read cell when `figure` is null, and the card shows its trip in state `read-without-calendar`. The board is unchanged for them (no figure to rank). Folded into the design's table.
4. **Dates outside the search's window** (departed, or the search's dates changed; old alert links): card state `outside-window`, "These dates are outside this search's dates now.", linking back to the search; the window test is the board's (`datePairIndexer(currentSpace(def, todayLondon))` non-null), checked before scope parsing so the route answers 200.
5. **A booking address belongs to one pairing.** The API attaches `bookingUrl` to a pairing only when the list's booking read is that pairing's (`booking.attempt`/`returnIndex` equal the pairing's, status in `BOOKING_WITH_OFFERS`), the same rule `pairingOffer` uses for offers. Otherwise null, and the price says "Find on Google Flights ↗".
6. **The board's pairing group carries `bookingUrl`**, so a read trip's price is its booking link on every row, open or closed.
7. **Trips cards (the first screen) link a trip's price to its Trip page in stage 1**; the cards' booking targets come with stage 2's card redesign (the cards contract carries no booking inputs today). Folded into the design's §6.2.
8. **The path rule applies where the address enters** (the worker answer and the DB insert); a stored address is read back as any string, and `bookingTargetOf` re-checks it, so a later change to the booking path degrades to "Find", never to a read error. The column has no CHECK constraint (a departure from 0012's pattern: a CHECK makes drizzle-kit rebuild the table).
9. **Old links:** `view=results` with dates lands on `trip` keeping `def`, `depart`, `return`, `d.from`, `d.to`, `d.journey` and dropping `basis`, `row`, `sort`, `f.*`; `view=results` with only `row=` (pre-revision-48 alert emails) lands on the search's page. The `row-lookup` landing and `RowLanding.tsx` go.
10. **On the Trip card, the price and the booking text are one link** (one anchor, one tab stop): "£412 · Book on Google Flights ↗". On a board row the price is the link and the row's date cell links to the Trip page; a row click still opens the row in place, and the price link stops propagation.
11. **Results' API reads stay** (`GET /results`, the cell route) for History and the alert builders; stage 4 removes what's left. Only the web Results view goes.

## Review Focus

1. **A pair whose newest list failed but an older list's trip leads:** the card shows that trip with a "couldn't read at 16:42" line above it, never a different price, and the line is absent whenever the board's figure has no failed newest list. Tests in Tasks 5 and 6.
2. **A booking address that isn't this pairing's or isn't the booking page** (another attempt's booking read, another path, another host, a query-only change, over 2048 characters): no "Book", only "Find on Google Flights ↗". Tests in Tasks 1, 4 and 5.
3. **The Trip page opened with the search page's filters on** (`d.journey`, `d.from`, `d.to`): the card's figure, its flight list, its booking target and "Read flights again" all use the filtered row's airport pair. Tests in Tasks 5 and 7.
4. **An old alert link** (`view=results&basis=verified&row=…`) for departed dates: lands on the outside-window state, 200, not an error. Tests in Tasks 5, 6 and 7.
5. **A long seller name or airline list at 375 px** ("Trip.com Travel Singapore Pte Ltd", three carriers): wraps, no sideways scroll. Playwright spec in Task 7.
