# Settings: Implementation Plan (UX redesign stage 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the interim Settings page with the designed one (Price sources, Limits, Email and alerts, System), so the operator changes keys, new-search sources, the browser's stopping rule, limits and email in the app instead of in `.env`/`app.env`, and sees SearchApi's own balance.

**Architecture:** The settings the page owns move to a `settings` table under their env names. On a boot where a name has no row, its env line (if any) is imported once; from then on the table owns it, and an env line that differs is reported, never applied. The app parses the boot-fixed env first and refuses as today; under the app lock it lays the rows over the env and parses the full config through the one `core` schema. A stored value the schema refuses is set aside for that boot and reported, so a stored value never stops the app booting. A save is validated by parsing the would-be config and applies by restarting the app in its own process once no search is running; while a restart waits, new starts wait too. The browser worker is unchanged: the page shows its pages at once with the command that changes it.

**Tech Stack:** TypeScript 5.9, pnpm workspace, Vitest, zod 4, Hono, drizzle (SQLite), React 19, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-08-ux-redesign-design.md` §7.2 "Stage 3: Settings" and §8 (approved by Ian 2026-11-08), mockup `docs/superpowers/specs/2026-11-08-ux-redesign-mockups/04-settings.html`. Where design and mockup differ, the design governs; this plan's Rulings refine both and Task 8 folds them back in. It amends the main spec `docs/superpowers/specs/2026-10-14-flight-price-optimiser-design.md` (revision 71 now). Plan review record: `~/.cache/get-me-there/review-spec/2026-11-19-settings/0NBGuUcNVX/` (106 findings, all ruled into this revision). ## Global Constraints

- No `as` casts except `as const`/`satisfies`; brands only through core's helpers or zod.
- Tests are event-driven: no sleeps, no poll-until loops; clocks injected or faked; a reload test waits on the closed/listening events. A test that drives many pages states a 15_000 timeout.
- Public wording: the repo's wording rules apply to every doc, comment, test name and commit (the orchestrator gives implementers the three wording greps; run them before every push). Commit messages never name the vendor of the flight pages. Examples use London → New York or synthetic QQ*/AAA codes.
- **No secret leaves the app.** A key, token or password is never returned by any route, logged, put in an error, a URL or a snapshot. Routes give each secret as `{ set: boolean; last4: string | null }` (`last4` only for the two API keys, never a password). Every stored secret joins the boot's secrets list; a secret arriving in a request body joins that request's scrub list before anything can fail. One test helper `expectNoSecrets(values, sinks)` seeds distinctive values and checks the PUT 200/422 bodies, the email-test bodies (with a double that echoes credentials in its error), captured logs across a reload, and `/api/settings`.
- Words shown to the operator: the page's labels live once in core `SETTING_LABELS` (the api's 422 and the page both use them); every other new sentence goes in `COPY`. SearchApi's unit is "credits" everywhere it is new or touched (top bar, Settings, new-search note, the search's field); "searches" is never used for it. The rendered sweep (`renderedSweep.test.tsx`) covers each Settings section and bans "searches left".
- Money from the operator is parsed from the string by core `poundsToPence(text): number | null` (digits, optional `.d` or `.dd`; never `parseFloat`), tested with `0.29`→29, `1.15`→115, `35.55`→3555, `35`→3500, and `-1`, `1.234`, `£5`, `` refused.
- Every write route needs `Content-Type: application/json` and `X-Requested-With: get-me-there` and is declared in core's `ROUTES` with its zod schemas; partial records use `z.partialRecord`.
- **Layout checks:** every UI task calls `expectNoSidewaysScroll(page)` on Settings at 375 px and 1280 px in light and dark, and attaches those four screenshots beside `04-settings.html` with a line per visible difference. Section links are links with `aria-current`; a 422 sits beside its field through `aria-describedby`; save results go to a polite live region; an off or failing line says so in words, never by colour alone.
- `core` keeps 100% coverage and its mutation score; a pure file added to `core` goes in `packages/core/stryker.config.json`. Run each touched package's `pnpm run test` and typecheck before each commit, one package at a time; a contract change also runs `pnpm --filter @gmt/web run test`.
- **Before every push, run every CI step locally:** `pnpm lint`, `pnpm boundaries`, `pnpm casts`, `pnpm temp-dirs`, `pnpm -r typecheck`, `pnpm -r --workspace-concurrency=1 test`, `pnpm exec vitest run --project scripts`, `node scripts/check-mutation-globs.mjs`, `pnpm secret-scan`, `pnpm --filter @gmt/web e2e`.
- A changed test expectation is listed in its commit message with the rule change behind it. Tasks run in order, 1 → 8. The PR lands by squash-merge; plain fix commits are fine. Commit trailer: `MrReasonable <4990954+MrReasonable@users.noreply.github.com>`.

## Rulings made while planning

1. **Owned names** (`SETTINGS_NAMES` in `packages/core/src/config/settings.ts`, each `{ name; secret }`): `TRAVELPAYOUTS_TOKEN`*, `SEARCHAPI_KEY`*, `SEARCHAPI_PLAN`, `SEARCHAPI_BILLING_DAY`, `CAMOUFOX_BROWSER_WINDOW`, `FLIGHT_READ_PATIENCE`, `DISCOVERY_REFRESH_DAYS`, `NEW_SEARCH_DISCOVERY`, `NEW_SEARCH_VERIFICATION`, `MONTHLY_SPEND_CAP_PENCE`, `EXECUTION_MAX_CALLS`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `SMTP_USER`, `SMTP_PASS`*, `ALERT_EMAIL_TO`, `ALERT_EMAIL_FROM` (* secret). Everything else stays env-only, including `SEARCHAPI_TRIAL_USED` (its boot rule changes: a value above 0 is ignored, with the existing warning words, when the plan is `40usd`, instead of failing boot), `CAMOUFOX_ENABLED` and every worker-shared setting.
2. **One owner per name.** Pure `layerSettings(env, rows) → { merged; imports: OwnedName[]; envIgnored: OwnedName[] }` (core): a name with no row takes its env line, if any, and is listed in `imports`; a name with a row takes the row (`''` = unset) and, when its env line is present and differs, is listed in `envIgnored`. No digests are stored. Rows are written only by the page's PUT and by imports.
3. **Boot order** (both `main()` and the tool bootstrap `apps/api/src/bootstrap/tool.ts`): parse the env with the owned names left out (`parseBootConfig`), run today's refusals, lock wait, backup and migrations unchanged through `AppLock.acquire`; then, under the lock, read the rows, `layerSettings`, and `parseConfig(merged)`. If the parse refuses a field that is an owned name, that name's stored or imported value is set aside for this boot (`setAside`, the env/default used instead) and the parse is retried, at most once per owned name; a refusal of a non-owned name fails boot as today. Imports are written (one transaction, no `await` between read and write) only after the parse succeeds and never for a set-aside name. The tool bootstrap reads the same layered config and writes nothing. `buildPorts` splits into `openDatabase` (open, migrate) and `buildFromDb(config, db, …)` so the layered config is ready before the guard, providers and notifier are built. Boot logs imported, ignored and set-aside names (never values).
4. **Storage.** Migration `0014_settings`: `settings(name TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL CHECK (<isIsoTimestamp>))`; no name CHECK (the repo validates names through `z.enum(SETTINGS_NAMES)`, and a test round-trips every name). Values are stored as `.env` stores them (Ian, 2026-11-19); the database and its backups are already 0600 (`packages/db/src/backup.ts`), and docs/setup.md §0/§6 says backups now contain your keys.
5. **Saving.** `PUT /api/settings` takes `{ changes: Partial<Record<OwnedName, string | null>> }` (null = unset; a secret not named is kept); the body's secrets join the request's scrub list first. It lays the changes over the current rows and parses; a refusal is 422 `{ fields: { name: OwnedName; label: string; words: string }[] }` where `words` comes from core `settingRefusal(name, error)` (per-name sentences, no env names); nothing is saved. Valid: the changed names are written in one transaction and the response is `{ warnings: string[]; applies: 'now' } | { warnings; applies: 'after-runs'; running: string[] }` (`warnings` carries boot-style warnings, e.g. a spend limit below the plan's fees). The page sends only the fields the operator changed.
6. **Restart in place.** `main()` registers SIGTERM/SIGINT once; each pass loads config (Ruling 3) and boots; the running app's `closed` resolves `'reload' | 'stopped'`; a signal during a pass's close or boot ends the loop. A save asks `requestReload()`: it sets the engine's `closing` flag at once (so a start, resume, catch-up or flight read asked after it is refused with "Applying new settings: try again in a minute", and scheduled firings are left to the existing catch-up after the reload), then reloads when `executions.oldestInFlight() === null && engine.flightReadInFlight() === null`, checked on each run settle through the existing `RunWatch` (a second observer through `EngineOptions`). A run that pauses keeps its pause; it resumes under the new settings. Close follows shutdown's order (scheduler, engine drain, checkpoint, lock release, server close awaited); the next pass takes the lock without the other-holder wait. `GET /api/health` gains `bootId` (random per pass). A pass whose boot throws ends the loop with today's boot-failure code and log (the supervisor restarts it; the next boot sets aside what fails). `GET /api/settings` reports `pending: { running: string[] } | null` while a reload waits.
7. **The new settings.** `FLIGHT_READ_PATIENCE` (default 12, 3–50) replaces `CONFIRM_PATIENCE`; each run records the patience it used in `ConfirmSummary.patience` (absent on older runs = 12), and the engine's stop rule, the estimate and `apps/web/src/views/Dates/confirmWords.ts` read the run's own value. `DISCOVERY_REFRESH_DAYS` (default 7, 1–30) is new searches' `discoveryRefreshHours` (× 24). `NEW_SEARCH_DISCOVERY` / `NEW_SEARCH_VERIFICATION` are comma lists of provider ids or `none`; unset means today's draft (every configured free source for discovery, SearchApi ticked nowhere, on every plan). A listed source that isn't configured drops out of the draft. `newSearchDraft` (`apps/web/src/views/Searches/NewSearchForm.tsx`) takes its sources only from `/providers`' presets, which the api builds from these. `EXECUTION_MAX_CALLS` keeps its meaning (what a new search's SearchApi limit starts at); existing searches keep their own.
8. **Source switches.** A source's switch reads "New searches use it" / "Off for new searches"; the block says existing searches keep their own choice and change it on their Edit form. SearchApi has two boxes: "Check the cheapest trips each search finds" (verification) and "Also use it for the calendar (many credits per search)" (discovery); the switch is On when either is ticked, turning it On ticks the first, Off unticks both and stores `none`. `GET /api/settings` returns the effective lists (`newSearchSources: { discovery; verification }`), so an unset list renders as the draft it gives.
9. **The browser block.** With `CAMOUFOX_ENABLED` false it says how to set the browser up (`pnpm gmt setup --reconfigure browser`, docs/setup.md §14) and shows no controls. Otherwise: the status line (ready, consent date) from `/status`; "Pages at once: N" read from the worker's `/v1/status` with "change with `pnpm gmt setup --reconfigure browser`"; the stopping rule (patience), "May run: only during scheduled searches / any time" (`CAMOUFOX_BROWSER_WINDOW`), and Advanced's "Read a date's calendar price again after N days (new searches)". The unrecognised-page pause stays a fixed 1 h (spec revision 38 keeps classifier stops out of settings) and is not on the page.
10. **SearchApi.** Owned key, plan (select "Free trial" / "$40 a month") and billing day (1–28, shown only on `40usd`). The balance: `searchApiAccount(http, key) → Promise<SearchApiAccount | null>` calls `GET https://www.searchapi.io/api/v1/me` (Bearer) on its own http-kit id `searchapi-account` with limits like `camoufoxStatusHttpLimits` (`billable: 'never'`, no response cache, its own limiter, 10 s timeout), so it writes no ledger row, takes no reservation and works after the local cap is spent (measured 2026-11-19: two calls left `current_month_usage` and `searches_this_hour` at 0). `SearchApiAccount = { remaining; monthlyAllowance; periodEnd: IsoDate | null; fetchedAt }` from `account.remaining_searches`, `account.monthly_allowance`, `subscription.period_end` (a date in `SCHEDULER_TIMEZONE`; absent on the trial). `GET /api/searchapi/account` caches it 10 minutes, refreshes after a run that called SearchApi, and gives `null` without a key or on failure. One web helper `searchApiCreditsLine(account, budget, providers)` replaces `searchApiCallsLeft` for every caller (top bar, NewSearchForm, DefinitionForm, WhereToLook, SearchFields): "SearchApi: 38 credits left" (+ " · resets 1 Dec"), "as of 14:05" when older than 10 minutes, or, on `null`, the local count as "SearchApi: 51 of 100 credits left (this app's count)". The local cap stays the hard stop and its stop words name it.
11. **Email.** Gmail (address, app password, send-to; stored as `smtp.gmail.com`, 465, `implicit`, user = from = the address) or Other mail server (host, port, TLS, user, password, from, to); a stored `smtp.gmail.com` opens as Gmail. `POST /api/settings/email-test` takes the form's values; the stored password is used only when host, port, TLS and user equal the stored ones, else the body must carry one (422 otherwise, before any connection); TLS `none` follows the existing loopback rule; addresses pass the existing `isMailbox` (no CR/LF); connect and socket timeouts 10 s; a failure answers 502 with one of fixed words (refused, timed out, sign-in refused, not a mail server), never the server's reply or address. The one-a-minute limit is held at module level, shared with `POST /api/alerts/test-email`. "Remove email" unsets the seven names after an in-page confirm.
12. **Alerts in stage 3.** Settings › Email and alerts lists the existing rules (`GET /api/alerts`) through `ruleText` with "last sent", Edit (opens the Alerts view's form) and Delete (in-page confirm); no rules: "No alerts yet. Alerts come from a search's page." (the line to add them is stage 4, UX §8 decision 4); no email: the rules list says alerts can't be sent until email is set up. The single alert kind and the repeat choice are stage 4.
13. **System** lists `/api/status` checks one per line (what, words, fix) through `StatusCard`'s line form, refetching as Status does. Status' fixes for Travelpayouts, SearchApi and email point to Settings › Price sources / Email (web) and to the Settings address (CLI), not `--reconfigure`. Two new checks: `settings` warn "<label> in .env is ignored: Settings holds it. Remove the line from .env." (from `envIgnored`) and `settings` fail "Saved <label> isn't valid any more: set it again in Settings" (from `setAside`).
14. **Page.** `view=settings&section=sources|limits|email|system` (default `sources`); desktop side list, 375 px one row of links above the section; old Providers, Status and Alerts views keep their URLs; the top bar's health link goes to `section=system`. Each section has one Save; unsaved edits survive switching sections (state lifted to the page) and the side list marks a section with unsaved edits. After Save: "Saved. Restarting the app…" until `/api/health` answers with a new `bootId` (60 s; then "The app didn't come back: run pnpm gmt status"), or "Saved. Applies when <names> finish; new searches wait until then." while `pending` is set (shown on every load). Remove key / Remove email confirm in the page first. Key fields: `type="password"`, `autocomplete="new-password"`, cleared after save.
15. **CLI.** `gmt setup`'s first run still writes the owned lines to `app.env` (imported on first boot). `--reconfigure travelpayouts|searchapi|email` and the owned half of `--reconfigure browser` (`CAMOUFOX_BROWSER_WINDOW`) print "Change this in Settings: http://127.0.0.1:<port>/?view=settings&section=…" and exit 0 once the app has stored settings (`/api/settings` answers); before that they behave as today. `gmt status`' price-source check reads `/api/status` when the app answers and otherwise says "the app isn't running; price sources are kept in its Settings", never a false "no price source".

## Review Focus

1. **A save while a search runs:** it keeps its settings to its end; no new run starts under the old settings while the reload waits; the reload follows the last run's end of any kind (Task 3 test over succeeded, failed, cancelled, budget-paused, interrupted ends; a start asked while pending is refused with the words; a scheduled firing in that window is caught up after).
2. **A stored value that breaks boot** (an update tightens a bound; a bad `.env` line imported): the app still boots with that name set aside, Status names it, Settings fixes it (Task 1 tests for both, and that nothing is imported from a refused env line).
3. **An env line after the page owns the name:** never applied, reported once per boot and on Status (Task 1 and Task 7 tests).
4. **The restart itself:** no stale lock, no `EADDRINUSE`, signal handlers once, no leaked timers or handles across three passes; SIGTERM after a reload checkpoints and releases once (Task 3).
5. **Secrets on every egress path** through `expectNoSecrets` (Global Constraints), including the email-test route's changed-host case (422, no connection opened).
